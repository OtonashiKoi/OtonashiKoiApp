# equipmentGAME 原生遊戲化：技術選型與 Roadmap

> 目標：把目前以 Discord / 網頁為介面的 equipmentGAME，演進成一款**可下載的原生遊戲**（Steam + 手機），同時**保護現有 365 名玩家與經濟資料**。
>
> 本文是規劃文件，尚未動工。撰寫時點：2026-05-30。

---

## 0. TL;DR（給趕時間的你）

- **你不是從零開始。** 後端（API、即時推送、戰鬥邏輯、365 名玩家的資料、美術素材）幾乎都能直接留用。原生遊戲對你來說是「**多一個新前端**」，不是重做整套遊戲。
- **主推引擎：Godot 4**（個人開發、純 2D、零授權成本、能同時出 Steam / 手機 / Web）。強力替代：**Cocos Creator**（你最熟的 TypeScript，主攻手機時）。保守選：**Unity**（要最成熟的商業化與上架生態時）。
- **最關鍵的一項後端改造**：把戰鬥輸出從「中文文字戰報」升級成「**結構化事件流（戰鬥腳本）**」。戰鬥計算邏輯不用重寫，只要多輸出一份機器可讀的格式，原生客戶端就能照著「演動畫」。
- **務實路徑**：不要一次重做整個遊戲。先做一個 **Phase 0 垂直切片**（登入 → 看角色 → 打一場會動的戰鬥），用 1～2 週驗證整條技術鏈路與手感，再決定要不要全力投入。
- **最大風險不是技術，是內容生產**（美術、動畫、音效、UI）。這是壓垮個人開發者原生遊戲的頭號殺手，roadmap 已針對這點設計。

## 1. 現況盤點：你已經有的資產

### 1.1 後端能力（幾乎可全部留用）

| 類別 | 現況 | 對原生遊戲的意義 |
| --- | --- | --- |
| API 框架 | Express + MongoDB（`equipment_game`） | 客戶端直接打 REST API 即可 |
| 玩家 API | `src/api/routes/playerAppRoutes.js`（2200+ 行）：登入、角色資料、背包全套操作、戰鬥、聊天 | 客戶端要的核心端點**幾乎都有了** |
| 認證 | Discord OAuth2 → JWT（7 天） | 需為原生客戶端補一種「不靠瀏覽器 redirect」的登入流程 |
| 即時推送 | SSE（`/api/me/stream`）+ 已安裝 `ws`（WebSocket） | 原生客戶端建議走 WebSocket，後端基礎已具備 |
| 戰鬥核心 | `src/shared/`：`combatLoop`、`combatStats`、`effectEngine`、`pkCombat` | **純邏輯、後端權威**，原生客戶端只負責「演出」，天然防作弊 |
| 美術素材 | 怪物圖、道具圖（Cloudinary + 本地 `uploads/`） | 可動態下載 + 快取，不必重做基礎素材 |

### 1.2 內容規模（這是一款成熟遊戲，不是 demo）

來自 `docs/CURRENT_GAME_STATUS.md`：

- **365 名玩家**、369 份進度資料（← 有真實營運中的玩家基礎，不能推倒重來）
- 51 隻怪物、324 件道具、37 個任務、10 個職業徽章、世界王
- 10 個 Zone（新手 → 神話，部分尚未開放）
- 副系統：拍賣（auction）、交易（transaction）、邀請（invite）、麻將（mahjong）、賭場（casino）、寵物（pet）、掛機（idle）、簽到（checkin）、世界王（worldBoss）、直播位階（playerTier / stream / creatorAuth）

**重點**：內容廣度很大。原生客戶端若想「一次重現全部」會是數月起跳的工程。Roadmap 會用 MVP 切片，先做能形成完整體驗的最小集合。

### 1.3 戰鬥輸出的現況（關鍵）

`src/shared/combatLoop.js` 回傳：

```
{ outcome, roundLogs, totalDamage, finalMonsterHp, finalPlayerHp, combatStats }
```

其中 `roundLogs` 目前是**人類可讀的中文字串陣列**（程式碼是 `log.join("\n")`），例如：

```
⚡ 古城法師 施放【雷擊術】但未命中。
──── 🛡️ 石像鬼 的回合 ────
```

- 對 Discord / 網頁顯示「文字戰報」很完美。
- 但原生遊戲要「演動畫」，需要的是**機器可讀的結構化事件**，例如：
  ```json
  { "round": 3, "actor": "monster", "action": "skill",
    "skillKey": "lightning", "hit": false, "target": "player" }
  ```
- 好消息：**傷害、暴擊、連擊、閃避、格擋、技能判定的計算邏輯都已經在了**，只是「輸出成了文字」。把它改造成同時輸出結構化事件，是中等工程，**不需要重寫戰鬥數學**。

## 2. 核心架構決策

### 決策一：客戶端 = 呈現層，後端 = 權威

- 戰鬥、掉落、經濟、數值全部維持**後端計算**，客戶端只負責「呈現結果 + 接收輸入」。
- 這是原生遊戲防作弊的關鍵（玩家拿得到客戶端、能改記憶體）。你現在的架構**剛好就是這樣**，是巨大優勢——別把計算搬到客戶端。

### 決策二：原生遊戲與 Discord / 網頁「並存」，共用同一後端與帳號

- 不取代 Discord，而是新增一個更沉浸的入口。三端（Discord / Web / 原生）共用同一份玩家資料與經濟。
- 好處：保護現有 365 玩家、後端已驗證、降低風險、玩家可無縫切換裝置。
- 帳號以 **Discord 身分為主鍵**（你現在就是用 `discordId`），原生客戶端登入後拿到同一個 JWT。

### 決策三：需要為原生客戶端「補」的後端能力

| 待補項目 | 為什麼 | 工程量 |
| --- | --- | --- |
| **結構化戰鬥事件流**（戰鬥腳本） | 客戶端要照腳本演動畫（見 §4） | 中 |
| **原生登入流程** | OAuth redirect 在原生 App 體驗差，建議 Discord「device authorization flow」或內嵌登入頁取 JWT | 中 |
| **WebSocket 即時通道** | 原生引擎對 SSE 支援不一，WebSocket 更通用（你已裝 `ws`） | 小～中 |
| **資產資訊 API + CDN 快取策略** | 客戶端動態下載怪物/道具圖並快取 | 小 |
| **客戶端版本檢查 / 強制更新** | 原生 App 無法像網頁即時更新，需要「最低版本」守門 | 小 |
| **請求簽章 / 防濫用** | 客戶端公開後 API 會被嘗試濫用，需 rate limit + 關鍵操作驗證 | 中 |

## 3. 引擎技術選型

針對你的條件：**個人開發者、JS/Node 背景、純 2D、已有 2D 素材、要 Steam + 手機、要複用 REST 後端、營運中（365 玩家）**。

| 維度 | Godot 4 ⭐主推 | Cocos Creator | Unity |
| --- | --- | --- | --- |
| 語言 | GDScript（類 Python，極好上手）/ C# | **TypeScript（你最熟）** | C# |
| 2D 體質 | 專為 2D 設計，一流 | 2D 強 | 3D 引擎做 2D，夠用 |
| 授權成本 | **完全免費開源、無版稅** | 免費開源 | 免費額度後分級收費；有定價信任陰影 |
| 引擎重量 | 輕（編輯器數十 MB） | 中 | 重 |
| Steam 桌面 | GodotSteam 外掛，成熟 | 較弱、非主流 | **Steamworks.NET 最成熟** |
| 手機（iOS/Android） | 支援（iOS 簽章需 Mac） | **手機體質最佳** | 支援，工具最全 |
| Web 匯出 | 支援 | 支援 | 支援（較重） |
| HTTP / WebSocket | **內建** `HTTPRequest` / `WebSocketPeer` | 內建 | 內建 |
| 商業化 SDK（IAP/廣告/分析） | 生態較小 | 偏特定生態 | **最齊全** |
| 學習資源（英文） | 多且成長快 | 較少 | **最多** |
| 適合場景 | 個人 2D、成本掌控、Steam+手機 | 沿用 TS、手機優先 | 擴團隊、最成熟商業化 |

### 建議

- **主推 Godot 4**：個人開發純 2D RPG 的當前最佳解。零授權風險、2D 體質最好、內建網路、Steam/手機/Web 全覆蓋。GDScript 雖要新學，但你做的是回合制 RPG（不吃極限效能），上手很快。
- **強力替代 Cocos Creator**：如果你「極度想沿用 TypeScript 技能」且**手機優先於 Steam**，這是最省學習成本的選擇——甚至部分純邏輯（數值公式、效果判定）能從現有 JS 移植成 TS。
- **保守選 Unity**：如果你預期未來**擴團隊**、或要最成熟的 IAP / 廣告 / 分析 / 上架生態，Unity 仍是最穩的工業標準（接受其授權模式與引擎重量）。

### 補充：一條「務實折衷」的第四條路（誠實告知）

你已經有一個 Web SPA（`src/web/public/app/`）。理論上可用 **Tauri / Electron 打包成桌面 App 上 Steam**、或 **Capacitor 打包成手機 App**——複用最多、最快「可下載」。但**畫面與手感天花板明顯低於原生引擎**（本質還是網頁渲染）。你既然明確選了「畫面與手感最強的原生遊戲」，本文主軸採原生引擎；這條路列在這裡只是讓你知道有此選項，未來若想快速先有「可下載版本」可考慮。

### 配套技術（不分引擎）

- **網路層**：HTTPS REST（既有 API）+ WebSocket（即時）。客戶端封裝一個 API client + JWT 管理 + 重連。
- **資產**：怪物/道具圖走 CDN 動態下載 + 本地快取；角色/特效動畫打包進客戶端。
- **發行**：Steam（需 $100 上架費 + Steamworks）、Google Play（$25 一次）、App Store（$99/年 + 需 Mac）。

## 4. 戰鬥演出協議（最關鍵的技術設計）

這是讓「原生遊戲畫面好做」的核心，也是你目前最大的缺口。

### 現況 → 目標

| | 現在 | 目標 |
| --- | --- | --- |
| 戰鬥計算 | `combatLoop.js`（已完成、後端權威） | 不動 |
| 輸出格式 | 中文字串 `roundLogs`（給人看） | **再輸出一份結構化「戰鬥腳本」**（給機器演） |

### 戰鬥腳本（Battle Script）長相（建議）

後端打完一場戰鬥，除了現有文字戰報，另外輸出一份事件時間軸：

```json
{
  "outcome": "win",
  "seed": 123456,
  "actors": {
    "player": { "job": "swordsman", "weaponType": "sword_1h", "maxHp": 5200 },
    "monster": { "id": "...", "name": "石像鬼", "maxHp": 6400, "imageUrl": "..." }
  },
  "timeline": [
    { "t": 0,   "actor": "player",  "type": "attack",
      "weapon": "sword_1h", "damage": 820, "crit": true, "combo": false,
      "targetHpAfter": 5580 },
    { "t": 700, "actor": "monster", "type": "skill", "skillKey": "lightning",
      "hit": false },
    { "t": 1400,"actor": "player",  "type": "execute", "damage": 5580,
      "targetHpAfter": 0 }
  ]
}
```

客戶端拿到後：照 `timeline` 的時間戳，播放「揮劍 → 暴擊特效 → 傷害數字跳出 → 血條下降」。

### 為什麼這個設計好

- **計算與演出徹底分離**：戰鬥平衡照舊在後端調，客戶端只管好不好看。
- **三端共用**：Discord 用文字版、網頁與原生用腳本版，同一場戰鬥一次算出。
- **武器/職業已分類**：`combatLoop` 已有 `weaponType`（sword_1h / dagger / staff / bow…）與 `archetype`（swordsman / mage / archer / healer…），可直接對應動畫資源。
- **可重播 / 可驗證**：帶 `seed` 還能做戰鬥重播與爭議排查。

> 這一項建議列為 **Phase 0 必做**——它是後續所有戰鬥畫面的地基。

## 5. 內容範圍與 MVP 切片

把現有系統分層，原生客戶端按優先級逐步納入：

| 層級 | 系統 | 是否進 MVP |
| --- | --- | --- |
| **核心迴圈** | 登入、角色資料、背包/裝備、戰鬥演出、升級/屬性、商店 | ✅ MVP 必含 |
| **經濟社交** | 拍賣、交易、任務（每日/每週/職業）、世界王、排行榜 | 🔶 Phase 2 |
| **副玩法** | 麻將、賭場、寵物採集、掛機、簽到 | 🔸 Phase 3 |
| **直播整合** | 直播位階綁定、彈幕/SC 覆蓋層、OBS | ⏸ 後期或維持網頁版 |

**第一個「可玩版本」(MVP) 的體驗閉環**：
登入 → 看自己的角色與裝備 → 選區域出戰 → **看一場會動的戰鬥** → 拿到掉落與經驗 → 升級、換裝、再戰。

這個閉環就足以證明「它是一款有畫面的遊戲」，且只動用到你**已經最成熟的系統**。

## 6. 分階段 Roadmap

> 工作量級距假設：**個人開發 + AI（我）輔助 + 複用現有後端**。以「相對級距」表示，不是精確人月——實際取決於你投入的時數與美術產能。

### Phase 0 — 技術驗證（垂直切片）｜級距：1～2 週

**目標**：跑通整條鏈路，確認手感與選型。
- 後端：新增「結構化戰鬥腳本」輸出（§4）；新增原生登入端點（拿 JWT）。
- 客戶端：用選定引擎做最小場景——登入 → 拉 `/api/me/profile` 顯示角色 → 打一場 quick-battle → 照腳本演出「攻擊/暴擊/血條/傷害數字」。
- **產出**：一個能在你電腦上跑、會動的戰鬥 demo。
- **決策點**：看完 demo 再決定是否全力投入、以及最終引擎。

### Phase 1 — 核心可玩｜級距：數週～約 1–2 個月

- 大廳 / 角色面板 / 背包與裝備管理（接現有 equip / unequip / use / sell / enhance API）
- 完整戰鬥場景（多區域、多怪物、Boss、掉落動畫、升級演出）
- 商店、屬性加點、職業呈現
- 客戶端 API client + JWT + WebSocket 即時 + 錯誤處理 + 載入/快取
- **產出**：核心戰鬥成長迴圈完整、可內測的版本。

### Phase 2 — 經濟與社交｜級距：數週

- 拍賣行、玩家交易、任務系統（每日/每週/職業）、世界王、排行榜、聊天
- 與現有 Discord 經濟完全互通
- **產出**：和現有網頁/Discord 功能對齊的完整版。

### Phase 3 — 副玩法與打磨｜級距：數週～視內容量

- 麻將、賭場、寵物、掛機、簽到
- 音效、音樂、轉場、UI 動效、新手引導、設定選單
- 效能優化、多解析度適配（手機）
- **產出**：體驗完整、接近上架品質。

### Phase 4 — 發行｜級距：數週（含審核等待）

- Steam 商店頁、成就、雲存檔；手機商店上架
- 版本更新管線、強制更新、客服/回報、隱私政策（你已有 `privacy.html` / `terms.html`）
- 封測 → 公測 → 上線
- **產出**：可下載的正式版。

## 7. 美術與音效 Pipeline

這是原生遊戲品質的關鍵，也是工作量大宗。

| 資產類型 | 現況 | 取得方式 |
| --- | --- | --- |
| 怪物 / 道具圖 | ✅ 已有（Cloudinary） | 直接用；必要時補動畫幀 |
| 角色職業動畫 | ❌ 缺（待命/攻擊/受擊/施法/死亡） | 依風格：像素風可用 Aseprite 製作；插畫風可用骨骼動畫（Spine / DragonBones）或 AI 生圖 |
| 技能 / 打擊特效 | ❌ 缺 | 引擎粒子系統 + 特效素材 |
| UI 介面 | 🔶 有網頁版可參考 | 重新針對遊戲畫面設計（Figma） |
| 音效 / 音樂 | ❌ 缺 | 授權音效庫 / 委外 / AI 生成 |

**我能在這塊直接幫忙**：我這邊可接 **Aseprite**（製作像素角色/怪物/特效逐幀動畫）、**AI 生圖**（概念圖、UI 素材、貼圖）、**Figma**（UI/UX 設計）。實際能幫多少取決於你的**美術風格**——如果是像素風，Aseprite 路線很順；如果是現有那種插畫/渲染風，會偏向骨骼動畫 + AI 輔助。**這點需要你先定調美術方向。**

## 8. 風險與務實建議

| 風險 | 說明 | 對策 |
| --- | --- | --- |
| **內容生產無底洞**（頭號風險） | 美術/動畫/音效/UI 的量遠超後端，是壓垮個人原生遊戲的主因 | 嚴守 MVP 切片；先用既有素材；美術方向定調後批量產 |
| **範圍蔓延** | 想「一次把 10 個系統全做進去」 | 按 §5 分層，MVP 只做核心迴圈 |
| **帳號 / 經濟遷移** | 365 名玩家的資料與經濟不能出錯 | 三端共用同一後端，不遷移、不重置；只新增前端 |
| **作弊** | 客戶端公開後可被改 | 維持後端權威（決策一）；關鍵操作伺服器驗證 + rate limit |
| **發行門檻** | Steam/手機上架費、審核、iOS 需 Mac | Phase 4 預留時間與預算；可先上 Steam 再上手機 |
| **學習曲線** | 新引擎需要時間 | Phase 0 垂直切片就是用來「便宜地」確認你吃不吃得下這套工具 |

**最重要的一句建議**：**先做 Phase 0，再決定全力投入。** 用 1～2 週的垂直切片驗證「引擎順不順手 + 戰鬥演出好不好看 + 技術鏈路通不通」，遠比直接埋頭做半年安全。

## 9. 分工：我能做的 vs 需要你 / 外部資源

| 工作 | 我（AI）能做 | 需要你 / 外部 |
| --- | --- | --- |
| 後端：結構化戰鬥腳本輸出 | ✅ 主力 | 你驗收 |
